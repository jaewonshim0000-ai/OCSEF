# Android App Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Package Familiar Place as an installable Android app (Capacitor 8) where calling, recording, photos, backups, Read aloud and lock-screen help all work on a real phone.

**Architecture:** Same React app, bundled into a Capacitor Android shell. Thin adapters (`native.ts`, `speech.ts`, backup save, storage) pick the native path when `Capacitor.isNativePlatform()`. One custom plugin, `LockHelp`, adds the lock-screen notification and a separate `showWhenLocked` activity that runs the web app in over-lock mode.

**Tech Stack:** React 18, TypeScript 5.9, Vite 7, Vitest 4. New: `@capacitor/core|cli|android@8.6.0`, `@capacitor/filesystem@8.1.5`, `@capacitor/share@8.0.3`, `@capacitor-community/text-to-speech@8.0.2`. Java 21, Android SDK command-line tools.

**Spec:** `docs/superpowers/specs/2026-11-14-android-design.md`

## Global Constraints

- Exact version pins as listed above, and no other new dependencies.
- The web build must behave exactly as before. Native paths only run when `isNative()` is true.
- Nothing personal appears in the lock-screen notification.
- In over-lock mode, only the locked help views render. The in-app keypad is never shown.
- Every task ends with `npm test` and `npm run typecheck` passing, then a commit whose message ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Copy: plain British English, as in the existing UI.

## Review Focus

1. **Share sheet cancelled:** "Last backup" must not change, and no error is shown.
2. **Over-lock mode reached by typed hash routes** (`#/today`, `#/setup`, `#/lock`): each must land on help.
3. **Notification permission denied:** the switch turns back off and says why. No crash.
4. **The web app with Capacitor installed but running in a browser:** download, `speechSynthesis` and the service worker still work.
5. **Old saved data without `security.lockHelp`:** it loads with the default (on).

### Task 4: Lock-screen help, web side

**Files:**
- Create: `src/lib/lockHelp.ts`
- Modify: `src/lib/types.ts`, `src/lib/defaults.ts` (`lockHelp: true`), `src/lib/seed.ts`, `src/app/nav.tsx`, `src/App.tsx`, `src/screens/setup/SetupSettings.tsx`
- Test: `src/test/app.test.tsx`, `src/test/repo.test.ts`

**Interfaces:**
- Produces:
  - `lockHelp.ts`: `setLockHelp(enabled): Promise<boolean>`, `isOverLock(): Promise<boolean>`, `requestUnlock(): Promise<void>`. All are no-ops returning false on web.
  - `Nav.overLock: boolean`.

**Tests first:**
- A new install has `security.lockHelp === true`. Old data without the field loads with true.
- In over-lock mode (with `isOverLock` mocked to resolve true): the app opens on help, `#/today` and `#/lock` resolve to help, and "Try PIN again" calls `requestUnlock`.
- In a real profile, Settings → Lock shows a "Get help from the lock screen" switch. Turning it off calls `setLockHelp(false)`. If `setLockHelp(true)` resolves false, the switch is off and the permission note shows.
- After setup finishes, `setLockHelp(true)` is called. In sample mode it's called with false.

**Implementation notes:**
- The store or nav runs an effect that keeps `setLockHelp(mode === 'real' && security.lockHelp)` in sync, guarded so it only calls when the value changes.
- On start, nav awaits `isOverLock()` before the first `restart()`. When true, it sets `overLock` and restarts locked on `/help`.
- In `apply`, when `overLock` is on, it resolves with `unlocked = false`, and a `lock` route becomes `/help`.
- In `App.tsx`, `LockedLive` gets `onTryPin = overLock ? requestUnlock : () => navigate('/lock')`.

### Task 5: Lock-screen help, native side

**Files** (under `android/app/src/main/`):
- Create, in `java/com/familiarplace/app/`: `LockHelpPlugin.java`, `LockHelpActivity.java`, `LockHelpNotifier.java`, `BootReceiver.java`
- Modify: `MainActivity.java`, `AndroidManifest.xml`

**Behaviour:**
- **`LockHelpNotifier`:**
  - Creates the channel `lock_help`: low importance, public visibility on the lock screen, no sound or badge.
  - `post(ctx)` builds an ongoing notification ("Familiar Place" / "Tap for help", small icon) whose PendingIntent opens `LockHelpActivity` (`FLAG_IMMUTABLE`).
  - `cancel(ctx)` removes it.
  - `isEnabled` and `setEnabled` use SharedPreferences `familiar_place`, key `lock_help`.
- **`LockHelpPlugin`** (`@CapacitorPlugin(name = "LockHelp", permissions = @Permission(alias = "notifications", strings = POST_NOTIFICATIONS))`):
  - `setEnabled`: on API 33+, request permission if it hasn't been granted. Denied → resolve `{enabled:false}`.
  - `isOverLock`: `activity instanceof LockHelpActivity && keyguardManager.isKeyguardLocked()`.
  - `requestUnlock`: `keyguardManager.requestDismissKeyguard(activity, callback)`. On success it starts `MainActivity` (`FLAG_ACTIVITY_NEW_TASK | CLEAR_TOP`), then `activity.finish()`.
- **`LockHelpActivity extends BridgeActivity`:** registers `LockHelpPlugin` before `super.onCreate`.
  - Manifest: `showWhenLocked="true"`, `taskAffinity=".lockhelp"`, `excludeFromRecents="true"`, `launchMode="singleTask"`, the same theme and configChanges as `MainActivity`, and not exported.
- **`MainActivity`:** registers `LockHelpPlugin` and posts the notification on create if it's enabled.
- **`BootReceiver`:** on `BOOT_COMPLETED`, if enabled, `LockHelpNotifier.post`. Registered in the manifest as exported, with the `BOOT_COMPLETED` intent filter.
- **Commit.** Compiling is checked in Task 6.
